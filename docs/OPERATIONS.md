# Эксплуатация tickets-app

## Исходники и локальный запуск

Основной репозиторий: https://git.hyperide.ai/ultrabricks/tickets-app . GitHub больше не является источником выпуска. `fj` управляет репозиторием/PR, обычный Git выполняет fetch/push через системный credential helper. Для текущего аккаунта используется URL `https://alex-mextner@git.hyperide.ai/ultrabricks/tickets-app.git`; пароль или токен в URL не помещается.

```sh
bun install --frozen-lockfile
bun run setup -- --demo --port 8888
bun run dev
```

Дефолт API — **8888**, UI — **5173**. Единственный источник дефолтов: `packages/config/development.mjs`. Setup сохраняет выбор в `.env.local`, не сбрасывает пароли и не очищает уже инициализированную SQLite. Повторять `API_PORT=8888` перед каждым запуском не нужно. `localhost` и `127.0.0.1` разрешены только локально при совпадающих порте и протоколе; production Origin проверяется строго.

**Не удаляйте `.env.local` и базы ради обновления кода.** Демо использует только локальную SQLite; production никогда не наполняется демо-аккаунтами.

## Настройки продукта

В **Settings → Security** владелец/администратор задаёт `allowed_email_domains`. Список хранится в БД, проверяется при выдаче и принятии приглашений. Пустой список не ограничивает домены. Сопоставление точное: `example.org` не разрешает `sub.example.org`; wildcard пока не поддерживается. Смена политики не выгоняет существующих участников. Это ограничение приглашений, не автоматическая регистрация любого адреса домена и не проверка владения почтовым ящиком.

Задачи, эпики, проекты и циклы создаются на страницах документа. Новая запись не публикуется, пока не нажата Create. Существующий текст сохраняется inline. При конфликте можно явно выбрать серверную версию или повторить свой вариант относительно показанной версии; молчаливого перезаписывания нет.

## Production: отдельная явная инициализация

Существующий Vercel-проект: `tickets-app`, команда `inventorems-projects`, project ID `prj_BicxQsqDlb394HzvMuXZKB883EdY`. Запланированный постоянный origin: `https://tickets-app-sandy.vercel.app`. Статус конкретного выпуска нужно проверять отдельно; наличие этого адреса в документации не означает готовую базу.

Neon: проект `autumn-brook-27632436`, production-ветка `br-sparkling-morning-b1bs7tl5`, база `tickets`. При последней проверке перед выпуском production был пуст. Применение миграций и создание владельца требуют явного подтверждения оператора. HTTP-запросы и frontend-сборка **не выполняют миграции**.

Обязательные серверные переменные Vercel: `DATABASE_URL`, случайный `AUTH_SECRET` не короче 32 символов, точный HTTPS `APP_URL`. Для фоновых интеграций — `CRON_SECRET`. В `VITE_*` секреты никогда не помещаются. Vercel Sensitive-переменные могут возвращаться из `vercel pull` как `[SENSITIVE]`; это заглушка, не настоящий пароль/DSN. Не сохраняйте её поверх работающих значений.

После проверки production-ветки оператор может один раз выполнить из приватного локального окружения:

```sh
bun --env-file=.env.production.local scripts/db.mjs migrate
bun --env-file=.env.production.local scripts/db.mjs bootstrap
```

Приватный файл должен содержать реальные `DATABASE_URL` / `DATABASE_URL_UNPOOLED`, `BOOTSTRAP_EMAIL`, `BOOTSTRAP_NAME`, новый `BOOTSTRAP_PASSWORD` и параметры workspace. Его не коммитят и не отправляют в чат; права доступа — `0600`. Bootstrap отказывается повторно создавать владельца, не изменяет существующий пароль. После успешной инициализации bootstrap-пароль удаляют из локального файла и сохраняют в менеджере паролей.

## Приватные вложения

Поддерживаются два независимых варианта:

- Vercel **private** Blob: `STORAGE_DRIVER=blob`, `BLOB_READ_WRITE_TOKEN` из приватного store.
- S3/R2: `STORAGE_DRIVER=s3`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`.

Нельзя использовать локальный диск serverless-функции как постоянное хранилище. Каждый upload/download проходит авторизацию workspace, проверку MIME/размера и существования задачи. API запрещает повторное завершение уже загруженного вложения. Дополнительно Blob запрещает перезапись на стороне хранилища; неоднозначный повтор Blob принимается только при совпадении байтов. S3-адаптер пока полагается на прикладную проверку и не заявляет атомарный no-overwrite контракт провайдера. Ограничения первого выпуска: 3 MiB/файл и 500 MiB/workspace. Антивируса и фоновой сборки физически удалённых объектов пока нет. При лимите 3 MiB Blob-ответ намеренно буферизуется с ограничением объёма до отправки; это примерно до 6 MiB временной памяти на активную загрузку, а не потоковое решение для больших файлов.

## Выпуск без GitHub

Используйте существующую CLI-авторизацию Vercel и заранее проверьте `.vercel/project.json`. Не создавайте второй проект и не публикуйте из другой рабочей копии.

```sh
bun run check
bun run typecheck:tsc
bun run check:secrets
vercel deploy --prod --skip-domain --yes --scope inventorems-projects
```

Это сборка Linux-кандидата без переключения постоянного домена. Она не требует выгружать Sensitive-секреты локально. До promotion проверьте candidate через `vercel curl /api/health --deployment URL` и `/api/ready`. Liveness `health` и готовность схемы/владельца `ready` — разные проверки. Кандидат с `not_ready` не является работающим production. На уникальном candidate URL браузерные записи могут отклоняться строгим canonical Origin — не ослабляйте эту защиту ради preview.

Только после подготовки базы и приёмки API:

```sh
vercel promote URL --scope inventorems-projects
```

После promotion проверьте на постоянном origin вход владельца, создание/редактирование задачи, перезагрузку, комментарий и приватное вложение. Успешная сборка не заменяет эти проверки.

Старую связь с GitHub следует отключить именно у этого Vercel-проекта, чтобы прежний репозиторий не публиковал устаревший код. Нативной связи с Forgejo в этой настройке нет: до включения собственного CI publisher используется CLI. Не переносите Vercel-токен в публичный репозиторий.

## Интеграции и границы приёмки

GitHub/Slack адаптеры проверяются подписанными синтетическими событиями и HTTP-тестами; доступ ассистента к сервису не передаётся приложению. Для живой установки нужны собственные credentials и явно выбранный workspace. В production оставляйте неподключённые модули выключенными. `bun run worker` обрабатывает один пакет durable inbox/outbox; расписание на хостинге настраивается отдельно. Сам факт очереди не подтверждает внешнюю доставку.

## Проверки и визуальные эталоны

`bun run test:ui` — Storybook с реальными browser interactions/axe. `bun run test:e2e` — Chromium; `bun --bun playwright test --project=webkit` — отдельная проверка WebKit. PostgreSQL suite требует явного `TEST_DATABASE_URL` изолированного тестового сервера и никогда не должен запускаться на production.

Скриншоты и pixel overlays находятся в `docs/screenshots/parity/`. `scripts/reference-audit.mjs` работает только с явно указанным локальным тестовым URL. В отличие от обычных визуальных regression-тестов, он сравнивает наш экран с публичным Linear demo, без масштабирования/сдвига. Другие данные, шрифт и неподдержанные модули не скрываются и не превращаются в выдуманный процент сходства.
