## Главный результат и статус приёмки

**State-lib теперь обслуживает настоящий inline issue editor, а не только тему/плотность.** Сохранение, ввод во время запроса, refetch, конфликты и восстановление черновиков прошли реальный UI в Chromium и WebKit. Ошибки сохранения настроек теперь видны пользователю; проверена межвкладочная синхронизация и сохранность неизвестной версии настроек.

**Заявление о большей скорости не подтвердилось, упрощение прикладного кода тоже. Конкретный lifecycle gate HYP-1499 теперь исправлен и проверен:** Runtime освобождается до изменения локальных флагов контроллера. Исходный RED сохранён и проходит; четыре дополнительные проверки защищают публикацию, подписки, активное сохранение и отказ из transaction/derive. Общая unit-suite — 215/215; реальные browser-сценарии повторены для обоих backend. Это закрывает конкретный дефект, но не является разрешением на production promotion и не доказывает остальные целевые свойства библиотеки.

## Реальное изменение архитектуры

`document-controller.ts` владеет документом, dirty/error/conflict/busy состояниями на одном Runtime. Derived dirty и внешний snapshot публикуются согласованно. Сохраняется существующий контракт `ticket-draft:<account>:<workspace>:<issue>` и функции versioned merge/draft acceptance. Запросы сериализуются; последующий ввод не заменяется более ранним ответом; неизвестная/непродвинутая версия ответа останавливает drain и сохраняет draft.

React binding подписывается через external-store, отзыв права публикации происходит при deactivate, окончательное освобождение отложено для StrictMode cleanup/setup. Родитель key-компонента включает пользователя, workspace и issue; старый контроллер не переносится в другой аккаунт. `data-document-backend` показывает действующий путь. Старая реализация сохранена в `document-baseline.ts`; тот же `VITE_STATE_BACKEND` выбирает и редактор, и preferences.

**Не заменены:** API/auth, TanStack Query server cache/optimistic transport, URL state, редакторы создания/планирования и локальные UI-состояния всех остальных компонентов. Они проходят регрессионные проверки, но не выдаются за новый normalized store. В этом смысле это полноценный подключённый issue-document workflow, а не перенос абсолютно каждого состояния приложения. Physical normalization, generated schema/FSM, query IVM и Wasm здесь не внедрены.

## Что исправлено в HYP-1498

Персистентность preferences получила явные состояния `ready`, `unavailable`, `read-error`, `invalid-data`, `unsupported-version`, `write-error`, `conflict`. Ошибки чтения и JSON разбора больше не смешаны с quota failure. Настройки остаются доступны в памяти; Settings показывает предупреждение и Retry.

Изменение только sidebar не записывает неизменившуюся persisted projection. Числовая версия, которую текущая программа не понимает, не перезаписывается version:0. Storage проверяется и перед записью, а не только при hydration. Событие из второй вкладки применяет совместимые значения без обратной записи. Если локальная запись уже провалилась, входящее изменение не уничтожает выбор пользователя: показывается конфликт, Retry явно сохраняет текущую вкладку. Обработчик `storage` снимается при dispose/HMR.

Это **app-adapter на Runtime**, не новый официальный общий API пакета. Read-before-write не является cross-tab compare-and-swap: между двумя вкладками всё ещё возможно состязание после проверки. Обычные совместимые preferences используют последнее наблюдённое значение, а не CRDT. Эти ограничения важны для исследовательской задачи; механизм нельзя автоматически перенести на несохранённый текст или деньги.

## Исправленный lifecycle-дефект HYP-1499

Последовательность: subscriber вызывает `controller.dispose()` во время публикации. Runtime правильно отвергает освобождение на notification boundary; но controller успевает выставить локальные `disposed=true`/`active=false`. Последующая нормальная попытка dispose ничего не делает, и Runtime с графом остаётся жив. Это нарушение cleanup/ownership, а не доказательство потери текста в каждом обычном редактировании.

Независимый тест: `disposal attempted during notification does not poison subsequent controller cleanup` в `tests/unit/state-lib-document.test.ts`. Ожидается сохранить committed state после отвергнутой операции, затем корректно закрыть Runtime обычным вызовом. Нельзя отключать этот тест ради зелёного статуса. В текущем исправлении этот тест проходит без изменения ожиданий. Повторное освобождение после отказа работает; повтор после успешного освобождения идемпотентен. Runtime/vendor не менялись. Общая задача интеграции остаётся In Progress: её последующие цели и production promotion этим исправлением не утверждаются.

## Размер, память и стоимость кода

Полный чистый build JavaScript: **1 342 180 → 1 351 657 B** (+9 477 B); сумма gzip ресурсов **416 774 → 420 136 B** (+3 362 B, около +0.81%). JS chunks: 8 → 9. Source maps исключены, CSS не изменён; это весь output, не initial-route transfer. Для каждого backend применён `vite build --emptyOutDir`: промежуточный повторный build без очистки оставил старые hashed chunks и исключён из результатов. Dynamic import сохраняет одну инициализацию backend, но добавляет асинхронную границу; её холодная сетевая цена отдельно не измерена.

Median JS heap после GC для description 100/10 000/50 000: baseline примерно 30,50/30,10/29,43 MB, state-lib 30,64/29,34/30,71 MB. Только три heap-снимка на условие, без native DOM memory; разнонаправленные различия не показывают устойчивой экономии памяти.

Оригинальный hook: **180 строк / 5802 B**. Новый controller + React binding: **340 строк / 10842 B**, отдельно от небольшого selector-barrel. Tests, сохранённый baseline и vendor не включены в этот прирост. Добавлены отдельная тестируемая ownership-модель и новые проверки, но **«меньше прикладной обвязки» пока не достигнуто**. Общий library lifecycle/persistence API должен уменьшить повторение этих обязанностей, не скрыв контракты за магией.

## Результат дополнительного review/fix
Независимое correctness-ревью нашло ещё один сценарий: совместимое внешнее событие могло заменить несохранённый выбор, запись которого была заблокирована будущей схемой (а не quota error). Новый RED воспроизвёл потерю light→dark. Guard теперь защищает любой unsaved local choice; совместимая схема восстанавливает возможность записи, но пользователю нужен явный Retry. Тест старой ветки дополнен более сильными ожиданиями conflict/local-retention и explicit retry, а не отключён. Все 7 persistence unit-контрактов и 4 реальные cross-tab/quota browser-проверки прошли. Этот исторический review предшествовал исправлению HYP-1499; актуальная проверка приведена выше.

Замечание о бесконечной загрузке identity проверено по текущему Workspace: он уже обрабатывает pending/401/прочие ошибки useMe до монтирования IssueDetails. В текущем маршруте этот дополнительный дефект не подтверждён; standalone-компонент вне Workspace не заявляется проверенным.

Уточнение целей: README reference-runtime прямо не обещает универсального ускорения. Таблица оценивает пользовательские целевые свойства и продуктовые намерения, а реализованные гарантии ядра перечислены отдельно. Замеры typing сделаны перед последней локальной правкой receive()-ветки; эта ветка не выполняется в одностраничном typing benchmark. Storage-сценарии и build повторены после исправления.
