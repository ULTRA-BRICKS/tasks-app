# Task activity shows what changed

User report, 29 September 2026 (UB-76 / 27b3f56d-de08-4912-a031-3dfdfbb36461): the task Activity lists only "Alex updated the issue" entries, so nobody can see which status, assignee, dates or description text changed. Activity is the task's audit trail; each update must name its fields with old → new values.

## What the stored history already contains (no migration)

- Native `updated` rows have stored `{ field: { from, to } }` for every editable field since the first tickets commit (d9771a6): `title`, `description` (full text before and after), `kind`, `status_id`, `priority`, `assignee_id`, `project_id`, `cycle_id`, `milestone_id`, `parent_id`, `estimate`, `start_date`, `due_date`, `position`, the `archived`/`deleted` flags, and `label_ids` as `{ from: [...], to: [...] }`. Linear team moves add `team_id` and `key`. The old presentation discarded all of it and printed a fixed verb, so **every existing native update is derivable** from the current `activity.data` column.
- Imported Linear history (`linear_imported_change`) stores Linear's from/to IDs for fields and labels. Linear records a description edit only as `updatedDescription: true`; its text is not in the history API, so **imported description diffs are not derivable**. They show "Description edited (Linear history does not include the text)", never a fake diff.
- Capture going forward needs no change: the writer already stores full before/after values. No production migration, re-import or audit rewrite is involved; the `activity` rows stay byte-identical.

## API contract

`GET /api/v1/issues/:id` activity rows keep `id`, `action`, `data` (immutable audit payload), `actor_name`, `created_at`, and gain:

- `summary`: the event verb without the actor: `updated the task`, `created the task`, `added a comment`, `archived the task`, `moved the task to trash`, `created the task in Linear`, …
- `changes`: ordered structured field changes:
  - `{ kind: 'value', field, label, from, to }` for status, assignee, priority, title, type, team, ID, project, milestone, cycle, parent task, estimate, start date and due date. `from`/`to` are display text: referenced records resolve to their names in the same workspace, cleared values to a readable empty label (`Unassigned`, `No due date`, …), missing records to `Unavailable …`, never a raw UUID. Assignee changes also carry `from_id`/`to_id`: the stored person ID (native) or the canonical person the Linear user maps to (imported), `null` when cleared or unmapped, so the client can show that person's avatar and card.
  - `{ kind: 'labels', field: 'labels', label: 'Labels', added, removed }` with every label name (arrays carry names only, never a count placeholder); an unchanged label set yields nothing. Name lookups are batched per table, not capped, so a resolvable record never reads as unavailable.
  - `{ kind: 'text', field: 'description', label: 'Description', from, to }`: full Markdown before/after for native edits; both `null` when the source did not record text (imported Linear).
- `details`: extra non-field notes (`reordered the task`, `updated task links: SRC-8`, `updated attachment: …`, a second imported verb such as `moved the task to trash`).

People (assignee values and imported Linear users) use the canonical person projection shared with the rest of the detail response; unknown or former members fall back to their stored account/source name, then `Unavailable person`. Imported references still resolve against the matching immutable import records (see IMPORTED-HISTORY.md). Unknown payload keys and action codes are never shown.

## Presentation

UB-100 (user report, 30 September 2026: «изменения стали 2 строчными … надо однострочно как раньше / диффы некрасиво показываются») replaced the UB-76 heading-plus-grid layout, where even one status change took two rows (`Alex updated the task` / `Status  Todo → Backlog`).

- **One change is one line**: `<Actor> changed <Field> <old> → <new>` with the entry time at the end of that line, e.g. `Alex Morgan changed Status Todo → Backlog` … `Sep 30`. The old value is muted, the new value is medium-weight text; assignee values with a person ID (`from_id`/`to_id`) show that person's avatar and open their card when the directory knows them, and an initials avatar with the stored name when it does not; values without an ID (`Unassigned`, other fields) are plain text. The line wraps only when the viewport cannot fit it; values break inside rather than widening the page.
- Other changes read the same way: labels inline as chips (`added label Bug`, `added labels Bug Frontend and removed Backend`), a description edit as `edited the description` with a `View changes` disclosure on the same line, an imported description edit as `edited the description (Linear history does not include the text)`. Events without field changes read `<Actor> <summary>` (`created the task`, `added a comment`) or their detail (`reordered the task`).
- **Grouped edits never get a heading**, whatever their count. The first line starts with the actor, each further change is its own one-line continuation that starts with its verb (`changed Assignee Unassigned → Alex Morgan`), aligned under the actor. A non-update verb that carries changes (an imported `archived the task` event that also moved fields) leads the entry and its changes follow as continuation lines. Details (`reordered the task`, `updated task links: SRC-8`) are continuation lines too.
- Description diff: the `View changes` / `Hide changes` disclosure is a button on the description line (`aria-expanded`, `aria-controls`), and the diff opens directly below that line inside the entry, so the line itself stays one line; the diff is computed only when opened. (UB-76 used `<details>`/`<summary>`, but a disclosure cannot sit inline in a sentence and put its panel below the line without nesting the line's person button inside `<summary>`.) A header names the field and counts changed lines (`−1 +1`, announced as "1 line removed, 1 line added"). Rows are line-based on a monospace 12 px / 20 px grid with a −/+ sign gutter; replaced lines highlight only the changed words. Colours come from the DTCG `success`/`danger` semantic tokens (tinted row, stronger word highlight) in both themes, and colour is never the only cue: gutter signs, visually hidden "Removed:"/"Added:" prefixes, `<del>` strike-through and `<ins>` underline. Unchanged runs keep two lines of context and collapse the rest into a `Show N unchanged lines` button that expands them in place. The diff box scrolls vertically inside itself (max 320 px) and wraps long lines, so neither the page nor the panel scrolls sideways. When the two versions total more than 4,000 lines (a pasted document would otherwise render one row per line) or the changed region needs more than a million line comparisons, the complete before and after texts are shown instead of a diff.
- Grouping: consecutive update events (native `updated` or imported field changes) by the same actor, each within 10 minutes of the previous one, merge into one entry with every change line in chronological order. Nothing is collapsed or deduplicated, so every individual field change stays inspectable. Created, commented, archived, trashed and restored events break a group; a native archive/unarchive (stored as an `updated` row with a bare `archived` flag) therefore gets the `archived the task` / `restored the task from the archive` summary rather than a detail line, matching imported history. The panel keeps showing the latest eight entries.
- Wording says Task, never Issue.
- Permissions: activity is part of the task detail, which already requires workspace `read`; every name lookup is scoped to the viewer's workspace, so no value from another workspace can appear. There are no per-field visibility rules for workspace readers.
- Phone (390×844, 320 px): the same one-line sentences wrap within the entry column (time stays at the end of the first line); the diff spans the entry column and scrolls inside its own box; the page never overflows horizontally.

## Decisions and rejected alternatives

- Structured `changes` computed on the server, not by the browser parsing `data`: one presentation for native and imported history, and clients never depend on storage keys.
- Diff in the browser from the provided before/after text, not a server-side diff: the texts are already in the response; no second endpoint or dependency. Rejected: lazy per-event diff endpoint (more routes for data already sent); third-party diff package (a small bounded LCS covers Markdown descriptions).
- Grouping on the client over the returned events: the API keeps one row per audit record.
- Rejected: collapsing repeated edits of one field inside a group into net old → new (hides intermediate values, violating "every change inspectable").
- UB-100: rejected a heading row for groups of three or more changes (the extra `updated the task` row is exactly what the user reported) and one comma-separated sentence per group (a description disclosure or a long title turns it into an unscannable paragraph). Rejected a label/value grid (`<dl>`): it forces the field onto its own column or row. Assignee IDs are sent by the server rather than matched by name on the client, because two people can share a name.
