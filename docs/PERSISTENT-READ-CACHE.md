# Persistent read cache — UB-39

Task identity: `95bca12c-d241-484f-8766-29489f818cc9` (UB-39, "Finish persistent cached workspace data and safe stable revalidation"). Before this change only the public application shell was cached ([MOBILE-SHELL-AND-LIVE-UPDATES.md](MOBILE-SHELL-AND-LIVE-UPDATES.md)); every start waited for the network before showing any workspace content.

## Behavior

A warm start renders the last **server-confirmed** copy of the workspace immediately, from IndexedDB, while `GET /api/v1/me` revalidates the session in the background.

- **Stale and read-only until confirmed.** A restored copy is labelled "Saved copy from <time>" (a strip at the top of the workspace, `SavedCopyNotice`) with the reason it is not yet live (checking, offline, rate-limited, server unavailable) and a Retry control. Every restored query is marked invalid, so mounted views revalidate at once. Until `/me` confirms the same account, the API client refuses every non-GET request except `/auth/*` with `READ_ONLY_SAVED_COPY` before touching the network; typed text stays in the existing drafts.
- **What is stored.** Only replies that a server fetch confirmed (never `setQueryData`: optimistic edits, rollbacks and restores are ignored) and only these query roots: `me`, `catalog`, `issues`, `issue`, `projects`, `cycles`, `milestones`, `views`. Auth options, API tokens, invitations, integrations, workspace policy, notifications and team-deletion previews are never written.
- **What is removed before storage.** Every email address at any depth, `catalog.modules[].config` (integration mappings such as Slack `user_map`), `catalog.imported_files` (pre-signed source URLs), and any field whose name looks like a credential (`token`, `secret`, `password`, `hash`, `oauth`, `signature`, `api_key`, invitation/reset fields), in snake_case or camelCase. `me` is stored only for interactive `session` actors, with a fixed field list. The stale frame may therefore show a person twice (email grouping in `canonical-people.mjs`) until the live catalog replaces it.
- **Partitioning.** Records are keyed by `[account id, workspace id]`. The device keeps one partition: confirming a different account deletes the other partition, resets that account's in-memory queries in this tab and tells other tabs to reset theirs.
- **Clearing.** Sign-out, any `401` (expired or revoked session) and an account switch delete the whole store and broadcast to other tabs through `BroadcastChannel`, with a `storage` event as fallback. Receiving tabs cancel in-flight requests, reset their query cache (their `/me` then returns `401` and shows sign-in) and wipe once more, so a write they committed before the message arrived is removed too. The server answers `401` only when a request carries no valid session (missing cookie, expired or deleted session, removed membership: `requirePermission`); a signed-in member without a permission gets `403`, and an integration's upstream `401` is reported as `403 SOURCE_ACCESS_DENIED`, so no other failure deletes the copy. Signing out after the session already ended (`/auth/logout` answers `401`) completes the sign-out instead of reporting a failure.
- **Late and early replies.** Each fetch is stamped with a session epoch that increments on sign-out, revocation and account switch; a reply from an older epoch or a removed query is never written. Every start revalidates the first screen in parallel with `/me`, so a reply that lands before `/me` confirms the session is held in memory and written only when `/me` confirms the same account in the same epoch; a sign-out, `401` or account switch drops it, and a later `setQueryData` on that query replaces it.
- **Bounded work, bounded retention.** At most 80 entries per partition (least recently saved evicted first; the account entry never), at most 5 pages per task list (the kept cursor continues Load more), at most 1.5 M serialized characters per entry, writes coalesced for 400 ms into one transaction. Entries expire **24 hours** after their last server confirmation and are deleted on the next start. Record format version `READ_CACHE_SCHEMA = 1`; any other version is discarded, not migrated. No `navigator.storage.persist()` request: the browser may evict the copy at any time and the app then starts cold.
- **Storage failures are explicit and never block work.** Missing IndexedDB (`unsupported`), denied storage (`denied`), an open that hangs for 3 s or throws (`failed`) and quota exhaustion (`full`, after evicting the oldest half once and retrying) each leave the app fully usable online and show a dismissible "offline copy" note. Sign-out resets `full` to `ready` after the wipe.
- **Revalidation problems.** Offline (browser offline or network error), `429` (honouring `Retry-After`, capped at one hour) and server errors keep the saved copy read-only and schedule a retry (15 s, 30 s, 60 s, then every 120 s); coming back online retries at once.

## Drafts on sign-out

Unsent drafts are kept on the device when the user signs out, as the ticket requires. They stay scoped to account and workspace (`draftBelongsTo`), so another account never sees them, and they reappear when the same account signs in again in that tab. When drafts exist, Sign out asks "Keep drafts and sign out" (default) or "Discard drafts and sign out". That answer settles the drafts, so the editors' browser "Leave site?" prompt is not shown again for the sign-out navigation (`allowUnload`, `src/shared/lib/unload-warning.ts`); without drafts Sign out has no dialog and the editors' prompt still guards any unsaved text. A revoked or expired session never deletes drafts.

## Decisions

Recorded review quorum: `/Users/ultra/xp/.tasks-work-evidence/read-cache-UB39-20260929/quorum-1.md` (29 Sep 2026; experts omp `anthropic/claude-opus-4-8`, `opencode-go/glm-5.3`, `opencode-go/kimi-k3`; moderator `anthropic/claude-opus-4-8`).

1. **Drafts on sign-out — converged 3/3 on option A3** (keep by default, explicit discard choice, `401` always keeps). The ticket criterion "revoke/logout clears private read cache across tabs but preserves unsent drafts" conflicted with `src/widgets/navigation/ui.tsx:52-59` (deleted `ticket-draft:`, `ticket-new:`, `plan-draft:` on sign-out) and `tests/e2e/inline.spec.ts:292-306` ("logout clears planning drafts as well as issue drafts"). The deletion was added without a stated rationale (commit `268d126`), destroyed the only copy of those drafts, and was inconsistent with durable knowledge drafts that sign-out never removed (`draft-persistence.ts:313-314`, "only after explicit confirmation"). The old test was replaced, not re-pinned.
2. **Personal data — converged 3/3 on option B2**: strip every email (members and imported `source_people`) and `modules[].config`; never request persistent storage; always delete on sign-out, `401` and account switch. Rejected: B1 (all emails at rest for a latency optimization) and B3 (member emails only — keeps most of the data and still splits people). A SHA-256 email grouping key (one expert) was not adopted: a hash of an email is still pseudonymous personal data.
3. **Retention — split.** Two experts: 24 hours since last confirmation; one: 7 days (the session cookie's `Max-Age=604800`, `packages/server/app.mjs:237`) to avoid a daily cold start. All three agreed that anything longer than 24 hours needs the product owner. The shipped value is the conservative 24 hours; extending it is escalated to the product owner and is not decided here.
4. **Owned IndexedDB layer instead of TanStack persisters.** Measured with Bun's minifier, external `@tanstack/query-core`: `@tanstack/query-persist-client-core` persisters + `idb-keyval` = 4,810 B raw / 1,848 B gzip; `PersistQueryClientProvider` + `idb-keyval` = 2,360 B / 1,097 B; the owned layer (`read-cache.ts` + `read-cache-policy.ts`) = 10,609 B raw / 4,139 B gzip. The owned layer is larger but those packages would still need the same custom code: `persistQueryClient` dehydrates the whole client (including optimistic data) into one blob per throttle tick, cannot partition by an account that is only known after `/me`, and has no epoch guard for late replies or cross-tab revocation; `experimental_createQueryPersister` restores lazily inside `queryFn`, which cannot render before revalidation. The layer uses raw IndexedDB with no new runtime dependency.
5. **Read-only rather than offline writes.** Linear queues offline edits and documents that it does not check change dates, so offline edits can overwrite teammates ([Download Linear — offline mode](https://linear.app/docs/get-the-app)). Tasks keeps versioned writes authoritative: nothing is sent until the session is confirmed, and writes after confirmation still carry versions, so an edit based on a stale copy is rejected with a conflict instead of overwriting.

## Out of scope

Offline writes or a mutation queue; caching documents/initiatives, notifications or settings screens; persisting search results; encrypting IndexedDB (the browser profile is the protection boundary, and sign-out deletes the copy); background sync. Playwright's offline emulation rejects Service Worker navigations in WebKit ([microsoft/playwright#42775](https://github.com/microsoft/playwright/issues/42775)), so the shell tests take the network away by closing the web origin instead of `context.setOffline`; the browser's `offline` event path is covered by unit tests.
